# 深度审查检查清单

按层次覆盖，避免只在局部文件里打转。

## 1. 产品设计层

对每个主功能都问一遍：

- 这个功能解决的用户问题是什么
- 不做它会造成什么用户成本
- 用户从哪里进入
- 用户如何完成主要任务
- 中途可能在哪些状态失败、取消、回退、恢复
- 用户是否会对能力边界产生误解
- 文案和交互是否诚实表达了当前实现能力

## 2. 架构设计层

对每个主模块都问一遍：

- 模块边界是否清晰
- source of truth 是否唯一
- 依赖方向是否单向、稳定
- 是否存在横切逻辑散落
- 组件拆分是否符合职责单一原则
- 当前结构是否利于后续新增需求
- 是否把应该集中管理的策略分散到多个 view / service

## 3. 代码实现层

对每条关键链路都问一遍：

- 输入校验是否完整
- 状态转换是否合法
- 派生值是否可能过期或漂移
- 是否存在重复计算、重复实现、死分支
- 日期、时区、locale、单位换算是否安全
- 持久化、恢复、导出、同步是否可能不一致
- 生命周期切换时状态是否会错乱

## 4. Apple 平台层

对每个用户可见能力都问一遍：

- 是否符合 Apple HIG 的基本交互预期
- 是否考虑 Dynamic Type、VoiceOver、可点击区域、语义标签
- 是否存在主线程阻塞或长任务无反馈
- 是否有权限请求时机不当、说明不清的问题
- 是否有 App Review、健康/隐私表达风险

## 5. 注释与上下文层

对每个核心类型和复杂方法都问一遍：

- 未来维护者是否能快速看懂“为什么这么设计”
- 重要约束、调用顺序、生命周期假设是否有注释保留
- 是否存在应该记录却没记录的 TODO / FIXME / 迁移说明
- 注释是否过时、误导、与代码脱节
- 是否有复杂规则只存在实现里，没有任何文档痕迹

## 6. 交叉验证方法

- 从产品文案反推代码是否真的做到
- 从代码能力反推 UI/文案是否过度承诺
- 从持久化模型反推 UI 状态是否可能失真
- 从架构边界反推 bug 是否只是表象
- 从一个 finding 横向搜索同类模式，避免只报单点
