# llmctl 当前架构

日期：2026-05-08

本文是当前实现的基线文档。`docs/架构设计文档.md`、`docs/架构优化方案.md`、`docs/稳定化复审与修复方案.md` 主要保留为迁移历史和设计过程，不再代表代码现状。

## 1. 设计目标

llmctl 的长期定位是：

1. 一个面向多 provider 的 CLI 探针。
2. 一个单运行时实现，只维护 `genai` 主执行路径。
3. 一个把配置、诊断、请求执行、输出展示分层清楚的工具，而不是自研第二套多 provider SDK。

## 2. 当前模块边界

```text
src/main.rs
  -> config/
  -> runtime/planner.rs
  -> runtime/genai_runtime.rs
  -> output/
```

### `config/`

职责：

- 加载 v2 YAML/JSON 配置。
- 合并 CLI、profile、defaults、环境变量。
- 生成唯一的 `ResolvedRuntimeConfig`。
- 在执行前给出 `--dry-run` / `--doctor-config` 可复用的诊断输入。

关键子模块：

- `schema.rs`：CLI 参数和 v2 配置模型。
- `resolver.rs`：优先级合并和 provider alias 归一化。
- `validate.rs`：配置合法性与能力诊断。
- `loader.rs`：只加载和校验 v2 YAML/JSON 配置。
- `converter.rs`：在 v2 YAML/JSON 之间做格式互转。

### `runtime/planner.rs`

职责：

- 判断当前解析结果是否可由 `genai` 运行时执行。
- 输出 dry-run/doctor 共用的运行计划诊断。

当前状态：

- 主路径只有 `genai`。
- 不再保留自动 fallback 到旧 `llm` runtime 的行为。

### `runtime/genai_runtime.rs`

职责：

- 从 `ResolvedRuntimeConfig` 构造 `genai::Client`。
- 统一处理 chat、stream、model list。
- 通过 `with_reqwest(...)` 注入 llmctl 自己管理的 `reqwest::Client`。

关键原则：

1. llmctl 不再自研 OpenAI 专用 HTTP 执行器。
2. provider 差异尽量留在配置映射层，而不是 runtime 分叉。
3. `extra_body`、reasoning、base_url、api_mode 都通过 genai 路径完成。

### `http/`

职责：

- 集中管理 llmctl 自己创建的 `reqwest::Client`。
- 统一 timeout、连接池、HTTP/2 keepalive、proxy 策略。

这层存在的意义是把 transport policy 从业务 runtime 中抽出来，避免以后每个 provider 或命令各自拼 `reqwest::ClientBuilder`。

### `output/`

职责：

- 普通输出、stream 输出、dry-run、doctor、错误信息统一格式化。
- 保证诊断信息不泄露敏感值，只显示来源，不显示 key 内容。

## 3. 配置优先级

当前遵循“同一语义只解析一次”的原则。

### Profile 选择

1. `--profile`
2. `active_profile`
3. 配置中的第一个 profile

### 典型字段优先级

- `model`：CLI `--model` > profile > adapter default
- `stream`：CLI `--no-stream` / `--stream` > profile > defaults > `true`
- `no_proxy`：CLI `--no-proxy` > profile > defaults > inherit reqwest/system proxy settings
- `api_key`：CLI `--secret/--key` > `api_key_env` / 默认环境变量 > `LLM_API_KEY` > config `api_key`

## 4. 代理策略

当前代理设计只有两种模式：

1. `inherit`
   - 默认模式。
   - 交给 `reqwest` 和平台网络栈决定。
   - 在 macOS 上可能会受到系统代理配置影响，即使 shell 中没有 `*_proxy` 环境变量。
2. `disabled`
   - 通过 CLI `--no-proxy` 或配置 `no_proxy: true` 显式启用。
   - 由 `reqwest::ClientBuilder::no_proxy()` 强制关闭 llmctl 自己管理的代理。

这样做的原因是：

1. 行为简单，可预测。
2. dry-run 可直接打印 `proxy_mode`。
3. 不需要修改第三方 `genai` 源码接口，只要注入自定义 `reqwest::Client`。

## 5. 为什么这是当前最优方案

相对于旧设计，当前方案的长期优势是：

1. 去掉了 `llm` 与 `genai` 双 runtime 分叉，问题定位成本显著降低。
2. transport policy 被集中到 `http/`，proxy/timeout 不会散落在各 provider。
3. 配置解析、能力诊断、执行路径职责分明，后续新增字段不需要在多个 runtime 同时维护。
4. vendor patch 只留在 `genai` 依赖层，llmctl 主代码不再承担自研 provider engine 的复杂度。

## 6. 后续演进建议

后续如果继续优化，建议优先做这三件事：

1. 等上游 `genai` 发布所需能力后，尽量缩小或移除 `vendor/genai` patch。
2. 继续补 transport/payload 级测试，覆盖 `base_url`、`api_mode`、`reasoning`、`no_proxy` 组合。
3. 如果配置项继续增长，再把 `ResolvedRuntimeConfig` 按 `request/auth/transport/output` 拆成子结构体，而不是重新引入多 runtime 抽象。
