# llmctl 稳定化复审与修复方案

> 历史说明：本文记录的是稳定化问题清单和整治方案。部分条目已经完成，部分结论对应旧运行时。当前代码基线请见 [当前架构.md](./当前架构.md)。

日期：2026-05-02

> 2026-05-02 更新：项目已决定取消 crates.io 发布，后续以 Homebrew/GitHub Release/`cargo install --git` 为安装路径。因此 `[patch.crates-io] genai = { path = "vendor/genai" }` 可以作为正式源码构建路径使用。本文早期关于“必须删除 `[patch]` 才能发布 crates.io”的结论仅适用于 crates.io 发布场景。

本文用于把当前阶段暴露出来的问题做一次批判性复审，并给出可落地的修复方案。目标不是继续针对单个命令打补丁，而是收敛运行时、配置语义、发布行为和测试门禁。

## 0. 当前落地状态

本轮已落地：

1. 恢复 `Cargo.toml` 中的 `[patch.crates-io]`，项目不再发布到 crates.io，源码构建统一使用 `vendor/genai`。
2. 新增 `RuntimePlanner`，dry-run、doctor 和执行路径共用同一份运行计划。
3. `extra_body` 不再自动 fallback 到 legacy；通过 `vendor/genai` 的 `ChatOptions::with_extra_body` 透传。
4. 新增显式 `--legacy-runtime`，仅作为临时兼容诊断入口。
5. Aliyun `--endpoint responses` 已路由到 `openai_resp::<model>` + 当前 base_url，不再静默 ignored。
6. legacy stream 空响应不再自动二次请求，改为明确错误。
7. init 模板不再默认配置 `extra_body.enable_thinking`。
8. `.gitignore` 已放行 `tests/cases/*.yaml`，CLI dry-run case 文件可正常进入版本库。
9. release workflow 已加入 fmt、clippy、test、release build 门禁，不再执行 `cargo package`。

仍未完全落地：

1. 发布版 genai 尚无 `extra_body` request passthrough；当前依赖 `vendor/genai` patch，后续可考虑向上游提交。
2. reasoning capability matrix 仍需继续细化到 provider/model 级。
3. stream mock/payload 级测试还需要继续补充，目前主要覆盖 resolver/planner/dry-run。
4. `--reasoning off` 已对 Aliyun/DashScope 注入 `enable_thinking=false`；其他 provider/model 仍需继续补充能力矩阵。

## 1. 复审结论摘要

当前判断成立：项目已经进入“修修补补导致行为分叉”的状态。核心问题不是某个 provider 的小兼容问题，而是以下四个层面互相打架：

1. 设计文档期望：genai 单运行时、`extra_body` 走 genai native、legacy 只做临时兼容。
2. 当前代码事实：只要 `extra_body` 非空，chat 会 fallback 到 legacy `llm` backend。
3. 本地构建事实：本地通过 `[patch.crates-io]` 使用 `vendor/genai`，包含本仓库临时 patch。
4. 发布事实：`cargo package` 不会携带 `[patch.crates-io]` 的 vendored genai，crates.io 用户使用的是上游 genai。

因此，本地测试通过不等于 crates.io 用户通过；某个 provider 能用不等于同一配置在另一个运行时还能用。

## 3. 根因分类

### 3.1 运行时边界不清晰

目前项目同时存在：

- genai runtime：`src/runtime/genai_runtime.rs`
- legacy llm backend：`src/provider/client.rs` + `src/builder.rs` + `src/backends/openai.rs`
- vendored genai patch：`vendor/genai`
- crates.io 上游 genai：发布后实际依赖

这些路径在请求构造、reasoning、stream、error、model list 上都不完全一致。只要继续保留“自动 fallback 到另一个 SDK”的设计，用户就会遇到同一命令因一个字段不同而行为改变。

### 3.2 CLI 语义没有做到可验证

`--endpoint responses`、`--reasoning off`、`--stream` 都是用户感知很强的语义参数。但当前实现中：

- `--endpoint responses` 对 Aliyun 不生效。
- `--reasoning off` 不保证服务端关闭 reasoning。
- `--stream` 失败时可能触发非流补偿请求。

这些都违背 CLI 工具的基本习惯：用户显式指定的参数必须要么生效，要么明确报错/警告。

### 3.3 发布链路没有保护架构假设

现有 release workflow 没有在发布前验证：

- 当前代码是否格式化；
- 单元测试是否通过；
- CLI dry-run cases 是否完整；
- `cargo package` 是否会用与本地一致的依赖；
- 发布包里是否包含测试用例；
- vendored patch 是否真的能影响 crates.io 用户。

这导致“本地好了，发布炸了”成为高概率事件。

## 4. 最佳解决方案

### 4.1 总原则

后续设计应遵循以下原则：

1. **一个主运行时**：chat/list/stream 默认只走 genai。
2. **无静默 fallback**：运行时切换必须显式、可诊断、可测试。
3. **显式语义必须可执行**：`--endpoint`、`--reasoning` 不能“看起来设置了但实际不生效”。
4. **provider 差异只存在于配置映射层**：llmctl 不再自研 provider engine。
5. **发布包行为必须等于 CI 行为**：不能依赖不会进入 crates.io 的本地 patch。
6. **错误优先暴露真实原因**：不要用二次请求掩盖 stream parser 问题。
7. **测试从 dry-run 扩展到 payload/transport 层**：不要只断言输出字符串。

### 4.2 推荐架构

```text
CLI Args
  ↓
Config Loader / Migrator
  ↓
ResolvedRuntimeConfig
  ↓
RuntimePlanner
  ↓
GenaiRuntime
  ↓
Output Formatter
```

新增或重构边界：

| 模块 | 职责 |
|---|---|
| `config::resolver` | 只做配置合并、alias 归一化、默认值填充 |
| `runtime::planner` | 决定 provider、protocol、reasoning、stream 能力是否可执行 |
| `runtime::genai_runtime` | 唯一主请求执行路径 |
| `runtime::payload_tests` 或 adapter wrapper tests | 对关键 provider 的 request payload 做离线断言 |
| `output` | 格式化响应、错误、dry-run、doctor |

legacy `llm` 路径改为：

- 默认不参与主路径；
- 仅保留为 `--legacy-runtime` 或内部兼容开关；
- 一旦进入 legacy，dry-run 和 doctor 必须显示明确 warning；
- 不允许自动因为 `extra_body` fallback。

### 4.3 依赖策略

最佳选择：**不要依赖本地 `[patch.crates-io]` 修复运行时语义**。

可选方案：

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 等 genai 上游发布包含所需能力的版本 | 升级到 crates.io 官方版本，删除 `[patch.crates-io]` | 推荐 |
| B. fork genai 并以 git dependency 固定 rev | 发布包也会使用同一 git rev | 可接受，但 crates.io 对 git dependency 发布有限制，通常不适合最终发布 |
| C. 保留 `[patch.crates-io]` | 本地有效，发布无效 | 不推荐 |
| D. 在 llmctl 内直接 HTTP 实现缺口 | 可控但违背“genai 单运行时” | 只允许短期 fallback，需删除计划 |

当前最优路径：

1. 列出必须依赖 genai 的能力：
   - `ChatOptions::with_extra_body`
   - OpenAI Responses streaming reasoning summary
   - OpenAI-compatible stream plain JSON error handling
   - Aliyun Responses 或兼容 OpenAI Responses 的路由能力
2. 如果上游 genai 已支持：升级版本，删除 `vendor/genai` patch。
3. 如果上游 genai 未支持：优先向 genai 提 patch，等待版本发布；短期内不要发正式 crates.io 版本。

### 4.4 OpenAI / Aliyun endpoint 设计

当前 `openai_api` 只对 `adapter: openai` 生效，这是不够的。应把 endpoint mode 从“OpenAI 专属字段”改为“OpenAI-compatible protocol mode”。

建议字段名：

```yaml
protocol: auto              # auto | chat_completions | responses
```

兼容旧字段：

```yaml
openai_api: responses       # legacy alias for protocol
```

映射规则：

| adapter | protocol | effective model / target |
|---|---|---|
| `openai` | `chat_completions` | `openai::<model>` |
| `openai` | `responses` | `openai_resp::<model>` |
| `aliyun` | `chat_completions` | chat/completions compatible target |
| `aliyun` | `responses` | responses compatible target |
| `openai-compatible` alias | `chat_completions` | `openai::<model>` + custom base_url |
| `openai-compatible` alias | `responses` | `openai_resp::<model>` + custom base_url |
| `anthropic/gemini/ollama` | 非 auto | validate error 或 warning，不要静默忽略 |

关键点：

- Aliyun 不能只映射到 `aliyun::model`，否则用户无法选择 `/responses`。
- 如果 genai 没有 first-class Aliyun Responses adapter，应该使用 `openai_resp::model + base_url=https://dashscope.aliyuncs.com/compatible-mode/v1/`。
- `--endpoint responses` 对兼容 OpenAI 的 provider 必须真的走 `/responses`，否则报错。

### 4.5 reasoning 参数设计

建议把当前 `--reasoning` 明确定义为“服务端 reasoning 控制”，而不是“展示/解析策略”。

```text
--reasoning off
--reasoning auto
--reasoning low|medium|high|xhigh|max
--reasoning budget:<n>
```

语义：

| 值 | 语义 | 不能做到时 |
|---|---|---|
| `off` | 尽可能关闭服务端 thinking/reasoning | 报 warning 或 error，不能只隐藏 reasoning |
| `auto` | 不主动设置 reasoning 参数，遵循模型/provider 默认 | 正常 |
| effort | 设置 provider 支持的 reasoning effort | 不支持则 warning/error |
| budget | 设置 provider 支持的 token budget | 不支持则 warning/error |

同时拆出一个内部字段，不暴露给普通用户：

```yaml
compat:
  reasoning_content_field: auto  # auto | reasoning_content | reasoning | none
  extra_body:
    enable_thinking: true
```

原则：

- `capture_reasoning_content` 只是“是否显示/捕获 reasoning”，不是“是否关闭 reasoning”。
- `--reasoning off` 不能只设置 `capture_reasoning_content=false`。
- `enable_thinking` 只作为兼容字段，由 provider capability 决定是否需要，而不是用户随手配置后就切换运行时。

### 4.6 stream 错误处理

应删除“空流后自动非流补偿”的主路径逻辑，替换为正确的 stream 错误解析。

推荐行为：

1. stream 建立前 HTTP status 非 2xx：读取 body 并返回错误。
2. stream 中出现标准 OpenAI error event：返回错误。
3. stream 中出现 OpenAI-compatible 顶层 `{code,message}`：返回错误。
4. stream 正常结束但没有任何 content/reasoning/tool/usage：返回 `EmptyStreamResponse` 错误，提示可用 `--no-stream` 诊断，但不自动二次请求。
5. 若确实需要二次请求，应由用户显式参数启用，例如 `--retry-non-stream-on-empty-stream`，默认关闭。

用户体验原则：

- CLI 工具不能悄悄发第二次模型请求。
- 空响应不是成功响应，应明确显示 provider/model/protocol/stream 信息。

### 4.7 model list 设计

当前静默 fallback 到 SDK 静态列表会误导用户。建议：

```text
llmctl -p aliyun --list
```

默认策略：

1. 先请求 live `/models`。
2. live 成功：输出 `source: live`。
3. live 失败：输出 warning，并在用户允许时 fallback。

新增参数：

```text
--list-source live|static|auto
```

默认：

- `auto` 可以 fallback，但必须显示 `source: static fallback` 和失败原因摘要。
- `live` 失败就报错。
- `static` 明确使用 SDK/内置列表。

### 4.8 CLI 参数收敛

建议保留：

| 参数 | 语义 |
|---|---|
| `-P, --profile <name>` | 选择配置文件里的 provider profile |
| `-p, --provider <preset>` | 无配置或临时切换内置 preset |
| `--protocol/--endpoint <mode>` | 选择 OpenAI-compatible protocol |
| `--reasoning <mode>` | 服务端 reasoning 控制 |
| `--stream` / `--no-stream` | 控制输出流式 |

改进：

- help 文案明确 `--provider` 不是 profile name。
- `--provider` 命中已有 profile 名时给提示：`did you mean --profile <name>?`
- `--preset` 不建议保留，避免和 `--provider` 重叠。

### 4.9 init 模板修正

init 配置应避免默认进入不稳定路径。

建议：

- OpenAI profile 保守使用 `openai_api: auto` 或 `protocol: auto`。
- Aliyun profile 默认使用 `qwen-plus` 或明确的稳定模型，不默认 `glm-5`。
- 不默认写 `extra_body.enable_thinking: true`。
- reasoning 示例放注释里，并说明哪些模型支持。
- 增加 `--dry-run` 示例，让用户先确认最终 runtime/protocol/model。

### 4.10 测试策略

当前 dry-run cases 是必要的，但不够。应扩展为四层：

| 层级 | 测试内容 | 是否联网 |
|---|---|---|
| resolver 单测 | config/CLI 合并、profile/provider/protocol/reasoning 解析 | 否 |
| planner 单测 | 是否能执行、是否 warning/error、是否 fallback | 否 |
| payload 单测 | 不同 provider/protocol/reasoning 生成的请求 JSON | 否 |
| mock stream 集成测试 | SSE、plain JSON error、空流、usage、reasoning chunk | 否 |
| live smoke test | Aliyun/OpenAI/Gemini 等真实调用 | 是，手动或 nightly |

必须补的用例：

1. `-p aliyun --endpoint responses` 必须真的路由到 `/responses` 或明确报错。
2. `--reasoning off` 对 Aliyun Chat Completions payload 应包含正确的关闭字段，或明确 warning。
3. `--reasoning off` 不能只关闭 capture。
4. `extra_body` 不应触发 legacy fallback。
5. stream 顶层 `{code,message}` 必须报错。
6. stream 正常结束但无内容必须报 `EmptyStreamResponse`。
7. `cargo package` 产物必须包含测试数据，或者测试不依赖被 `.gitignore` 忽略的文件。

### 4.11 发布门禁

release workflow 发布前必须执行：

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test --all-targets
cargo package --allow-dirty
./scripts/run-cli-dry-run-tests.sh
```

此外：

- 不能依赖 `[patch.crates-io]` 才能通过测试。
- `Cargo.toml` 增加 `repository`、`homepage` 或 `documentation`。
- 版本号只从 Cargo package metadata 读取；CLI `--version` 使用 `env!("CARGO_PKG_VERSION")`。

## 5. 分阶段实施计划

### Phase 0：冻结发布

在以下问题解决前，不发布新 tag：

- vendored genai patch 与 crates.io 行为不一致；
- `extra_body` fallback；
- `--endpoint responses` 对 Aliyun 不生效；
- stream 空响应二次请求；
- 测试 YAML 未被 git 正常跟踪。

### Phase 1：建立 Planner

新增 `RuntimePlan`：

```rust
pub struct RuntimePlan {
    pub backend: RuntimeBackend,
    pub adapter: String,
    pub model: String,
    pub protocol: ProtocolMode,
    pub reasoning: ReasoningPlan,
    pub stream: bool,
    pub warnings: Vec<Diagnostic>,
    pub errors: Vec<Diagnostic>,
}
```

目标：

- dry-run/doctor/execute 都使用同一个 plan；
- 不再在 `main.rs` 里临时计算 fallback；
- 所有“是否支持”都集中在 planner。

### Phase 2：移除自动 legacy fallback

修改策略：

- `extra_body` 不再 fallback；
- unsupported adapter 才允许 legacy，但必须 warning；
- 增加 `--legacy-runtime` 才能主动使用 legacy。

### Phase 3：协议路由统一

将 `openai_api` 重命名或内部映射到 `protocol`：

- `auto`
- `chat_completions`
- `responses`

Aliyun/OpenAI-compatible 都支持该字段。不能支持时 validate error。

### Phase 4：reasoning 能力矩阵

建立 provider/model 级 reasoning capability：

```text
supports_effort
supports_budget
supports_disable
supports_reasoning_content
supports_enable_thinking_extra_body
```

短期可用 provider 级；长期可细化到 model pattern。

### Phase 5：stream 错误模型统一

定义统一错误：

```rust
EmptyStreamResponse
ProviderError { status, code, message, request_id }
ProtocolNotSupported
ReasoningControlNotSupported
```

删除默认二次请求。

### Phase 6：发布链路修复

- 删除或替代 `[patch.crates-io]`。
- CI 增加质量门禁。
- `.gitignore` 放行 `tests/cases/*.yaml`。
- `cargo package` 后验证包内文件。

## 6. 二次复审：方案是否正确

### 6.1 对“只保留 genai 主运行时”的复审

结论：正确。

理由：

- 项目定位是 CLI 探针，不是 SDK。
- 继续维护 genai + llm + 自研 OpenAI 兼容逻辑，会导致能力矩阵指数级膨胀。
- 用户更关心“参数可预测、错误清楚、配置好懂”，而不是内部自动切换多个 engine。

风险：

- genai 某些能力可能暂时不完善。

处理：

- 能力缺口应进入 genai 上游或明确标记 unsupported，不应在 llmctl 内长期重写。

### 6.2 对“删除自动 fallback”的复审

结论：正确，但要分阶段。

理由：

- 自动 fallback 破坏可预测性。
- fallback 会改变 request payload、stream parser、error 格式。
- 用户无法从命令本身判断实际走了哪条路径。

风险：

- 某些旧配置短期不可用。

处理：

- 提供 `--legacy-runtime` 和迁移提示；
- dry-run 明确告诉用户如何迁移。

### 6.3 对“endpoint/protocol 泛化到 OpenAI-compatible”的复审

结论：正确。

理由：

- Aliyun 官方兼容 OpenAI Chat Completions 和 Responses，用户自然期望同一个参数可控。
- `openai_api` 这个名字让它看起来只属于 OpenAI，但实际是协议选择。

风险：

- 不是所有兼容服务都支持 Responses。

处理：

- `protocol=responses` 不支持时必须明确错误；
- `protocol=auto` 由 provider/preset 决定保守默认。

### 6.4 对“reasoning off 必须代表服务端关闭”的复审

结论：正确。

理由：

- 用户输入 `--reasoning off` 的直觉是“不要思考”，不是“不要把思考打印出来”。
- 如果只是关闭 capture，会隐藏成本和延迟问题。

风险：

- 各 provider 的关闭字段不同。

处理：

- 建 capability matrix；
- 不支持关闭时 warning/error；
- `capture_reasoning_content` 保持为单独配置，不混同 reasoning control。

### 6.5 对“stream 空响应不自动补发”的复审

结论：正确。

理由：

- CLI 不应未经用户同意重复模型请求。
- 补发非流请求会掩盖真正的 stream parser/provider 协议问题。

风险：

- 用户遇到空流时少了一个自动恢复。

处理：

- 错误提示建议用户手动运行 `--no-stream`；
- 如确需自动恢复，提供显式 opt-in 参数。

### 6.6 对“测试扩展到 payload/mock stream”的复审

结论：必须做。

理由：

- 真实 provider 测试不可稳定依赖。
- dry-run 只证明配置解析，不证明请求真的正确。
- payload 和 mock stream 能捕获绝大部分回归。

风险：

- 需要对 genai 请求构造做可观察封装。

处理：

- 先为 llmctl 自己的 planner 和 mapper 建测试；
- genai 内部无法观察的部分用 mock HTTP server 或 upstream tests 覆盖。

## 7. 当前不建议做的事

1. 不建议继续在 legacy stream 上补逻辑。
2. 不建议把更多 provider-specific 字段塞进 `extra_body` 后再 fallback。
3. 不建议在 crates.io 发布依赖 vendored patch 的版本。
4. 不建议继续扩大 `llm` backend 的职责。
5. 不建议用真实 Aliyun 请求替代自动化回归测试。
6. 不建议把 `--reasoning off` 文档解释成“兼容解析策略”。

## 8. 推荐的下一步

优先级顺序：

1. 修 CI/发布一致性：删除或解决 `[patch.crates-io]` 依赖问题。
2. 建 `RuntimePlanner`，把 dry-run/doctor/execute 统一到同一个 plan。
3. 让 `extra_body` 走 genai；不能走就阻塞发布，不再 fallback。
4. 重新设计 `protocol`，让 Aliyun/OpenAI-compatible 的 `/responses` 可控。
5. 重做 reasoning control，把“服务端控制”和“显示/捕获”拆开。
6. 删除 stream 空响应二次请求，改成明确错误。
7. 补 payload/mock stream 测试和 release 门禁。

这轮完成后，llmctl 的行为才会重新变成可预测、可发布、可维护。
