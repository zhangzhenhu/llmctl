# llmctl 基于 genai 的架构优化方案

> 2026-05-02 稳定化更新：项目已取消 crates.io 发布，后续以 Homebrew/GitHub Release/`cargo install --git` 为安装路径。当前落地策略允许通过 `[patch.crates-io]` 使用 `vendor/genai`，以获得 `extra_body` passthrough 和 OpenAI-compatible stream 兼容修复。

## 1. 最终决策

本项目后续采用 **genai 单运行时架构**。

核心决策：

1. 主 SDK 选用 `genai`，不再继续维护多套 provider engine。
2. llmctl 只负责配置解析、provider profile 选择、genai 参数映射、输出格式化、错误展示和配置迁移。
3. 所有聊天请求必须通过 `genai::Client` 发起，不再新增 OpenAI 专用 HTTP client。
4. 不使用 OpenAI 官方 SDK。项目必须支持 Anthropic、Google/Gemini、Ollama 等多平台，OpenAI 官方 SDK 不适合作为主依赖。
5. 当前自定义 `openai_reasoning.rs` 属于历史兼容代码。迁移到 genai 后，应删除或停止扩展，`reasoning_content` 交给 genai 的 reasoning stream/normalization 能力处理。
6. OpenAI 的 `responses` 与 `chat_completions` 作为配置项保留，并通过 model namespace 强制路由（`openai_resp::` / `openai::`）；不在 llmctl 内手写第二套 OpenAI 实现。

一句话目标：**llmctl 是 genai 上的一层 CLI 探针，不是一个自研多 provider SDK。**

## 1.1 当前实现进展（2026-05-02）

已落地（代码已实现）：

1. v2 配置加载与解析链路已接入主流程：`load_app_config -> resolve_runtime_config -> validate_resolved_config`。
2. `--dry-run`、`--doctor-config` 已可用，且包含 key 来源脱敏输出（不输出 key 内容）。
3. OpenAI `openai_api` 已支持 **可执行的 enforce**：
   - `responses` -> `effective_model=openai_resp::<model>`
   - `chat_completions` -> `effective_model=openai::<model>`
4. `genai` 已升级到 `0.6.0-beta.18`，并启用 `aliyun` 原生 adapter（`dashscope/aliyun -> adapter: aliyun`）。
5. 新增 genai runtime 主路径（`src/runtime/genai_runtime.rs`）：
   - 非流式 chat（`exec_chat`）
   - 流式 chat（`exec_chat_stream`，支持 reasoning chunk 输出）
   - list models（`all_model_names`）
6. 主流程已接入 `RuntimePlanner`：
   - 默认优先走 genai。
   - 不再因为 `extra_body` 等能力缺口静默回退 legacy。
   - 只有显式 `--legacy-runtime` 时才进入 legacy llm backend。
   - `--dry-run` 输出 `runtime_backend` 与 `runtime_fallback_reason`。
7. `LegacyReasoningContent` 不再触发 `provider_for_legacy_backend=openai-compatible` 的特殊重写；legacy provider 名保持与 adapter 一致，避免误走历史分支。
8. legacy fallback 的 provider client 已收敛到单一路径（`LLMBackendEnum::Standard`），不再在 client 层走 `OpenAIWithReasoning` 分支。

### 1.3 `openai_reasoning.rs` 下线清单（执行版）

为避免迁移后反复“回头加逻辑”，`src/backends/openai_reasoning.rs` 按以下顺序下线。
当前状态（2026-05-02）：前 4 项已完成，第 5 项已执行。

1. 保持不编译：`src/backends/mod.rs` 不再声明 `pub mod openai_reasoning`。
2. 保持不引用：`builder`/`provider client` 禁止出现 `OpenAIWithReasoning` 和 `build_openai_compatible` 调用。
3. 行为对齐门禁：
   - `cargo test` 全绿；
   - 至少一条真实 provider 请求（如 aliyun）成功；
   - `--dry-run` 显示 `runtime_backend: genai`。
4. 文档对齐门禁：
   - 方案文档明确“genai 主路径 + legacy 单路径 fallback”；
   - `openai_reasoning.rs` 标注为 deprecated migration artifact。
5. 满足 1-4 后执行删除：
   - 已删除 `src/backends/openai_reasoning.rs`
   - 已删除 `src/provider/traits.rs`（该文件未纳入模块树）

当前仍在过渡（明确保留的临时行为）：

1. 非 genai 已覆盖 adapter 不再自动回退 legacy；当前会诊断为 unsupported，除非用户显式使用 `--legacy-runtime`。
2. `extra_body` 在发布版 genai 中尚不能透传；当前默认诊断为 unsupported，等待上游能力后再恢复 genai-native 透传。
3. `--reasoning off` 仍需 provider/model 级能力矩阵支撑，当前不能对所有 provider 保证服务端关闭思考。

## 1.2 批判性复核结论

再次复核后，方案中最容易导致实现跑偏的风险有 7 个，必须作为研发门禁处理：

1. **不能把 genai 能力假设成已满足。** 文档中的 genai API 映射必须先由 spike 验证，不能直接按想象写主路径。
2. **不能在配置里声明支持，却运行时静默不生效。** `openai_api` 如果 genai 无法 enforce，必须在 validate 阶段报错或在 `--dry-run` 中标明 `unsupported`；`extra_body` 在发布版 genai 不支持前必须明确报错。
3. **不能过早删除旧实现。** 旧 `llm` 主路径只有在 genai 覆盖非流式、流式、custom base_url、reasoning、模型列表最低能力后才能删除。
4. **不能泄露密钥。** `--dry-run` 和 `--doctor-config` 只能显示 key 来源，不能显示 key 内容，也不能显示 key 前后缀。
5. **不能让 `extra_body` 成为灰色地带。** 发布版 genai 当前不支持 request `extra_body` 透传，llmctl 不能静默忽略或自动 fallback。
6. **不能把 OpenAI-compatible 当作独立 adapter。** v2 配置中第三方兼容 OpenAI 的服务统一使用 `adapter: openai + base_url`，旧配置中的 `openai-compatible`、`dashscope`、`aliyun` 只在迁移层转换。
7. **不能让 `system` 再退化成 user message。** system 消息必须进入 genai 的 system/instruction 能力；如果 genai 对某 adapter 不支持，必须 warning 或 fail，不能静默改 role。

对应门禁：

```text
Gate A: genai spike 完成前，不改主请求路径。
Gate B: extra_body 映射到 genai 的单元测试未通过前，不删除旧路径。
Gate C: reasoning stream 映射到 genai ReasoningChunk 的测试未通过前，不删除 openai_reasoning.rs。
Gate D: OpenAI API endpoint enforce 未验证前，显式 openai_api 非 auto 默认失败。
Gate E: dry-run/doctor-config 脱敏测试未通过前，不允许合并。
```

如果 Gate A/B/C 任一失败，不能继续任务 6 之后的主路径替换；应先修 genai 上游、调整依赖版本，或回到方案评审。

## 2. 设计边界

### 2.1 llmctl 负责

- 读取 YAML/JSON 配置。
- 支持一个文件内多个 provider profile。
- 解析 `active_provider`。
- 处理 CLI 覆盖项。
- 从环境变量读取 API key。
- 将 llmctl 配置映射为 genai 的 `Client`、`ChatRequest`、`ChatOptions`。
- 将 genai 的普通响应和流式事件格式化为终端输出。
- 提供 `--dry-run` / `--doctor-config`，打印最终运行计划。
- 保留旧 flat config 到 v2 config 的迁移兼容。

### 2.2 llmctl 不负责

- 不再维护自定义 OpenAI Responses HTTP 实现。
- 不再维护自定义 Chat Completions HTTP 实现。
- 不再维护自定义 SSE parser，除非是非常小的临时 fallback，且必须有删除计划。
- 不再新增 `OpenAIResponsesEngine` / `OpenAIChatEngine` / `OpenAIChatLegacyReasoningEngine`。
- 不再把第三方 `reasoning_content` 扩展成项目内部独立 engine。

## 3. 目标配置模型

推荐配置版本：`version: 2`。

```yaml
version: 2
active_provider: openai_main

defaults:
  stream: true
  timeout_seconds: 60
  capture_usage: true
  capture_reasoning_content: true
  normalize_reasoning_content: true
  openai_api: auto
  reasoning_mode: auto

providers:
  openai_main:
    adapter: openai
    model: gpt-5
    api_key_env: OPENAI_API_KEY
    openai_api: auto          # auto | responses | chat_completions
    reasoning_effort: medium

  openai_chat_compat:
    adapter: openai
    model: gpt-4.1
    api_key_env: OPENAI_API_KEY
    openai_api: chat_completions

  dashscope_qwen:
    adapter: openai
    model: qwen3-max
    base_url: https://dashscope.aliyuncs.com/compatible-mode/v1
    api_key_env: DASHSCOPE_API_KEY
    openai_api: chat_completions
    reasoning_mode: legacy_reasoning_content
    extra_body:
      enable_thinking: true

  anthropic_main:
    adapter: anthropic
    model: claude-sonnet-4-5
    api_key_env: ANTHROPIC_API_KEY
    reasoning_effort: medium

  gemini_main:
    adapter: gemini
    model: gemini-2.5-pro
    api_key_env: GEMINI_API_KEY
    reasoning_effort: medium

  local_ollama:
    adapter: ollama
    model: llama3.1
    base_url: http://localhost:11434
    api_key: ""

context:
  - role: system
    content: You are a helpful assistant.
  - role: user
    content: Hello.
```

### 3.1 字段说明

| 字段 | 说明 |
|---|---|
| `active_provider` | 默认使用的 provider profile 名称 |
| `providers.<name>.adapter` | genai adapter/provider 名称，例如 `openai`、`anthropic`、`gemini`、`ollama` |
| `base_url` | 自定义 endpoint，映射到 genai target resolver/custom endpoint |
| `api_key_env` | API key 环境变量名 |
| `api_key` | 直接写入配置的 key，不推荐，但保留 |
| `openai_api` | OpenAI API 偏好：`auto`、`responses`、`chat_completions` |
| `reasoning_mode` | reasoning 兼容策略：`auto`、`standard`、`legacy_reasoning_content` |
| `extra_body` | provider 额外请求字段；通过 genai 原生能力透传，llmctl 不做 provider-specific body 适配 |

默认 API key 环境变量：

| adapter | 默认环境变量 | 备注 |
|---|---|---|
| `openai` | `OPENAI_API_KEY` | 如果配置了 `api_key_env`，以配置为准 |
| `anthropic` | `ANTHROPIC_API_KEY` | 如果配置了 `api_key_env`，以配置为准 |
| `gemini` / `google` | `GEMINI_API_KEY` | 兼容 `GOOGLE_API_KEY` 可作为后续增强 |
| `ollama` | 无 | 默认允许空 key |

旧 provider alias 迁移：

| v1 provider | v2 adapter | v2 附加规则 |
|---|---|---|
| `openai` | `openai` | 无 |
| `openai-compatible` / `openai_compatible` | `openai` | 保留 `base_url`，`openai_api=chat_completions` |
| `dashscope` / `aliyun` | `aliyun` | 保留 `base_url`，`openai_api=auto`，如存在 thinking 配置则 `reasoning_mode=legacy_reasoning_content` |
| `gemini` / `google` | `gemini` | 无 |
| `anthropic` / `claude` | `anthropic` | 无 |
| `ollama` | `ollama` | 允许空 key |

### 3.2 CLI 覆盖规则

```text
--provider <name>       覆盖 active_provider
--model <model>         覆盖当前 provider.model
--url <base_url>        覆盖当前 provider.base_url
--secret / --key        覆盖当前 provider.api_key / api_key_env
--stream                覆盖 stream=true
--endpoint <mode>       覆盖 openai_api
--reasoning-mode <mode> 覆盖 reasoning_mode
--message <text>        追加到 context
--dry-run               打印解析后的运行计划，不发请求
```

配置优先级：

```text
CLI 参数 > 环境变量 > provider profile > defaults > 内置默认值
```

## 4. OpenAI API 选择策略

配置保留：

```rust
enum OpenAiApiMode {
    Auto,
    Responses,
    ChatCompletions,
}
```

落地约束：

1. 第一阶段不在 llmctl 内手写 OpenAI HTTP 逻辑。
2. 通过 model namespace 显式指定 OpenAI API：
   - `openai_api: responses` -> `openai_resp::<model>`
   - `openai_api: chat_completions` -> `openai::<model>`
3. `openai_api: auto` 使用 `openai::<model>`（SDK 默认 chat/completions 路径）。
4. 后续优先给 genai 增加上游能力，而不是在 llmctl 中另起一套实现。

这样可以避免项目重新滑回“多 engine + 自研 OpenAI SDK”的方向。

实现细则：

```text
openai_api=auto:
  允许运行，effective_model=openai::<model>。

openai_api=responses:
  effective_model=openai_resp::<model>，按 Responses Adapter 执行。

openai_api=chat_completions:
  effective_model=openai::<model>，按 Chat Completions Adapter 执行。
```

`--dry-run` 必须显示：

```text
openai_api_requested: responses
openai_api_enforced: true
openai_api_runtime: enforced_by_model_namespace
```

## 5. Reasoning 与旧式 reasoning_content

配置保留：

```rust
enum ReasoningMode {
    Auto,
    Standard,
    LegacyReasoningContent,
}
```

设计原则：

- `legacy_reasoning_content` 是兼容模式，不是独立 API。
- 优先使用 genai 的 reasoning capture/normalization 能力。
- 终端输出只关心标准化结果：Thinking 与 Response。
- 不再维护项目内自定义 SSE parser。

期望 genai 映射：

```rust
ChatOptions::default()
    .with_capture_usage(true)
    .with_capture_reasoning_content(true)
    .with_normalize_reasoning_content(true)
```

流式事件映射：

```text
genai ReasoningChunk -> Thinking 输出
genai Chunk          -> Response 输出
genai End            -> usage / captured content / duration 输出
```

如果某个 provider 的 `reasoning_content` genai 尚未正确归一化：

1. 先记录为 genai adapter bug。
2. 优先向 genai 提 patch/issue。
3. llmctl 不新增 parser 或适配层；应升级 genai 或修复 genai adapter。

## 7. Runtime 主流程

```text
load config file
  -> if v1 flat config: migrate to v2
  -> resolve active provider
  -> apply CLI overrides
  -> resolve api key from env
  -> validate unsupported capability
  -> build genai Client
  -> build ChatRequest
  -> build ChatOptions
  -> execute chat or stream
  -> format output
```

`GenaiRuntime` 建议接口：

```rust
pub struct GenaiRuntime {
    client: genai::Client,
    resolved: ResolvedProvider,
}

impl GenaiRuntime {
    pub async fn chat(&self, request: RuntimeChatRequest) -> Result<RuntimeChatResponse, LlmProbeError>;
    pub async fn stream_chat(&self, request: RuntimeChatRequest) -> Result<(), LlmProbeError>;
    pub async fn list_models(&self) -> Result<Vec<ModelInfo>, LlmProbeError>;
}
```

这里的 `GenaiRuntime` 不是 engine 抽象，只是把 genai 调用封装成当前 CLI 需要的入口。

## 8. genai 映射细节

### 8.1 ProviderProfile -> genai target

映射规则：

| llmctl 字段 | genai 目标 |
|---|---|
| `adapter` | genai adapter/provider |
| `model` | genai model name |
| `api_key` / `api_key_env` | genai auth resolver |
| `base_url` | genai service target resolver/custom endpoint |

### 8.2 context -> ChatRequest

规则：

- 顶层 `context` 作为默认消息。
- `--message` 追加为 user message。
- `role: system` 优先映射为 genai 支持的 system/instruction 方式；如果 genai 的 ChatRequest 只接受 user/assistant，则把 system 合并到 request/system instruction 字段，不能当 user message 发送。

### 8.3 generation options -> ChatOptions

字段映射：

| llmctl 字段 | genai ChatOptions |
|---|---|
| `temperature` | temperature |
| `max_tokens` | max_tokens / max_output_tokens |
| `top_p` | top_p |
| `reasoning_effort` | reasoning effort |
| `capture_usage` | capture usage |
| `capture_reasoning_content` | capture reasoning content |
| `normalize_reasoning_content` | normalize reasoning content |

### 8.4 extra_body

`extra_body` 使用 genai 原生能力。处理策略：

- llmctl 只负责从配置读取 `extra_body`，并映射到 genai 的 request options。
- llmctl 不按 provider 名称改写、补全或解释 `extra_body`。
- `extra_body` 中的敏感字段必须在日志、dry-run、doctor-config 中脱敏。

`extra_body` 门禁：

```text
extra_body 为空:
  可以运行。

extra_body 非空:
  必须通过 genai 原生 extra_body 能力透传。
  dry-run 显示 extra_body_supported=true。
  不允许本项目自定义 provider-specific body adapter。
```

原因：`extra_body` 往往用于启用 provider 特定能力，例如 DashScope/Qwen 的 `enable_thinking`。静默忽略会造成“看似开启 thinking，实际没开启”的错误验证结果。

## 9. list models 策略

目标：`llmctl -l` 仍然可用。

策略：

1. 优先使用 genai 提供的模型列表能力。
2. 如果 genai 只提供静态列表，输出时标记来源：

```text
Available Models (source: genai-static)
```

3. 对 OpenAI-compatible custom endpoint，如果 genai 不支持 live list，则保留一个独立的 `models` HTTP 请求 helper。
4. 该 helper 只允许用于 `list_models`，不能扩展成聊天请求实现。

这条例外是为了保持 CLI 探针能力，不违反“聊天请求全部走 genai”的原则。

## 10. dry-run 与 doctor-config

新增：

```bash
llmctl --dry-run
llmctl --doctor-config
```

`--dry-run` 输出：

```text
active_provider: dashscope_qwen
adapter: aliyun
model: qwen3-max
base_url: https://dashscope.aliyuncs.com/compatible-mode/v1
api_key_source: env:DASHSCOPE_API_KEY
stream: true
openai_api: auto
openai_api_enforced: false
reasoning_mode: legacy_reasoning_content
extra_body_supported: true
```

脱敏规则：

```text
允许输出:
  api_key_source: env:DASHSCOPE_API_KEY
  api_key_source: cli
  api_key_source: config

禁止输出:
  api_key: sk-...
  api_key_prefix: sk-...
  api_key_suffix: ...
```

dry-run 是可复制给他人的诊断输出，不能包含任何密钥片段。

日志脱敏规则：

- 默认日志级别不能打印请求体。
- 即使 `RUST_LOG=trace`，也必须对 `api_key`、`Authorization`、`extra_body` 中疑似密钥字段做脱敏。
- 错误对象中不能包含完整 URL query 中的密钥参数。
- 测试必须覆盖 `api_key` 不出现在 dry-run、doctor-config 和错误消息中。

`--doctor-config` 额外检查：

- active provider 是否存在。
- api key 是否可解析。
- base_url 是否为合法 URL。
- `extra_body` 是否已映射到 genai 原生 request options。
- `openai_api` 显式指定时是否可 enforce。
- provider adapter 是否被 genai 支持。

## 11. 开发阶段防跑偏规则

必须遵守：

1. 所有 chat/stream chat 请求必须通过 `genai::Client`。
2. 不新增 OpenAI 专用 HTTP client。
3. 不新增多 engine trait。
4. 不新增自定义 SSE parser。
5. 不继续扩展 `openai_reasoning.rs`。
6. genai 不支持的能力必须显式报 unsupported；genai 已支持的能力禁止自行适配。
7. endpoint/dialect/reasoning 只能作为配置与 genai option 映射，不作为分叉实现入口。

允许的例外：

- `list_models` 可以保留轻量 HTTP helper。
- `--dry-run` / `--doctor-config` 可以做协议能力检测。
- 为 genai 上游 patch 做临时代码实验，但不能进入主路径。

## 11.1 注释规范

本项目后续重构必须写必要注释，目标是让维护者快速理解“为什么这样做”，而不是重复代码在做什么。

必须写注释的位置：

1. **配置迁移规则。** v1 flat config 转 v2 profile 时，每个不直观映射都要说明原因，尤其是 `openai-compatible` 迁移为 `adapter: openai`、`dashscope/aliyun` 迁移为 `adapter: aliyun`。
2. **能力门禁。** `openai_api` 通过 model namespace enforce、`extra_body` 使用 genai 原生能力、`reasoning_content` 使用 genai normalization 的地方，要说明这是为了避免重新实现 SDK。
3. **system message 处理。** 任何处理 `role: system` 的代码都要说明不能退化为 user message。
4. **安全脱敏。** dry-run、doctor-config、日志、错误信息的 key 脱敏逻辑要说明不能输出 key 前缀/后缀。
5. **例外路径。** `list_models` 允许使用轻量 HTTP helper 时，必须注释说明该 helper 禁止被 chat 路径复用。
6. **删除旧实现的桥接代码。** 临时保留旧 `llm` 主路径、旧 provider 兼容层时，要写明删除条件和对应任务编号。

注释风格：

```rust
// v1 used provider names such as "dashscope" as pseudo providers.
// v2 maps dashscope/aliyun to the first-class "aliyun" adapter and keeps
// base_url so the runtime stays aligned with genai's provider model.
```

禁止的注释：

```rust
// Set the model.
config.model = model;

// Loop over messages.
for message in messages {}
```

验收要求：

- 新增 `resolver.rs`、`legacy.rs`、`mapper.rs`、`target.rs` 必须至少包含模块级注释，说明该模块在 genai 单运行时架构中的边界。
- 每个 `UnsupportedCapability` 分支必须有注释说明为什么不能在 llmctl 内自行补实现。
- 代码评审时，如果某段逻辑依赖本文档中的设计门禁，但代码没有注释，应视为未完成。

## 15. SDK 选择复核

最终选择：`genai`。

| SDK | 结论 | 原因 |
|---|---|---|
| `genai` | 选择 | 多 provider、custom endpoint、reasoning content、streaming 覆盖最贴近 llmctl |
| `rig` | 不选 | 更偏 agent/RAG 框架，抽象太重，容易牵引项目偏离 CLI 探针 |
| `multi_llm` | 不选 | provider 覆盖不足，缺 Google/Gemini 等关键目标 |
| OpenAI 官方 SDK | 不选 | 只解决 OpenAI，不满足多平台主目标 |

`genai` 仍有风险：

- OpenAI API endpoint 是否可显式指定需要 spike 确认。
- `extra_body` 通过 genai 原生能力使用，不做自定义适配。
- live model list 能力可能不足。

处理原则：

- 能力不足时优先上游 patch。
- 不在 llmctl 内复制一个新 SDK。
- unsupported 显式失败，不静默降级。
